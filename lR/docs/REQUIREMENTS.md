# luxuryRental M1 — 요구사항 정의서 v1.0
**작성:** 2026-11-02 · **상태:** 구현 범위/테스트 기준 설계 확정, 상업운영 정책 승인 미완료.
**프로젝트:** [lR](https://github.com/nalkarowndal/lR) | **원본 보존:** [M0 기능 대응표](FEATURE_MATRIX.md).
**범위:** 고객용 Android/iOS 앱 + Node.js API + ERP 관리자 웹 연계. 고급 디자인은 M2, API·DB 코드 구현은 M3 이후.

## 1. 목표와 사용자
- **고객:** 상품 검색, 명품 대여(일정·견적·결제), 구매, 수선/복원 접수, 찜/내역을 휴대전화에서 처리한다.
- **위탁 판매 신청자:** 브랜드/카테고리/상태/사진/견적 동의 후 위탁 접수 및 진행을 확인한다(초기 운영은 P1).
- **관리자/운영자:** 상품 실물 단위 재고, 예약 충돌, 출고/반납/검수, 주문, 수선, 에디토리얼, 감사 로그를 권한에 따라 처리한다.
- **매장 인력 관리자:** 기존 `RecruitApp`의 구인·근무자 관리 기능은 별도 웹 모듈로 유지(P2); 신규 고객 앱 하단 메뉴 아님.

## 4. 핵심 도메인 및 규칙
- **상품 != 개별 실물:** Product는 상품 모델/마케팅, InventoryUnit은 실물 고유 식별자.
- **대여 구간:** `[startDate,returnDate)` Asia/Seoul 달력 날짜. `returnDate > startDate`, 일수는 두 현지 달력 날짜 차이. 물류/검수 차단구간은 별도 `blockedStart/blockedEndExclusive`.
- **시간대:** 고객 날짜는 KST calendar date; 트랜잭션·만료·감사 타임스탬프는 UTC.
- **예약 트랜잭션:** 해당 실물 unit 행을 lock해 가용성/홀드/예약을 동일 트랜잭션 내 검증하고 멱등하게 기록. 서로 다른 실물은 병렬 예약 가능.
- **상태 권한:** 판매 완료/폐기/정비 상태는 예약 불가. 서버만 상태와 금액 최종 결정.
- **청구:** KRW 정수. RentalPrice = `dayRate * days - discount + shipping + optionalFees`, 보증금은 별도 표시 및 청구/보관 형태를 정책으로 분기. 할인·연장·손해배상은 PolicyVersion 고정. **예시 계산은 운영 가격 확정 아님**.
- **구매:** 미결제는 임시 홀드, 결제 성공 후 판매 확정. 실패/만료 취소 시 재고 재공개.
- **수선:** 고객 사진은 비공개 저장, IDOR 방지, 최소한의 메타데이터만 제공.
- **권한:** `CUSTOMER`, `ADMIN`, `INVENTORY_MANAGER`, `CARE_AGENT`, `CONTENT_EDITOR` 등 세부 역할은 M3 정책파일 확정. 브라우저 Role toggle은 인가 수단이 아님.

## 6. 범위 및 제외
이번 단계는 요구사항 문서/IA/ERD/API **설계만**. 실제 네이티브 앱, Node.js 서버, 마이그레이션, 실거래, PG 계약, 실사용자 데이터 수집은 수행하지 않는다. 출시 가능한 수준의 법률·사업 운영 프로세스는 별도 게이트로 남긴다.

## 7. 보류된 승인 목록
`DECISIONS_M1.md`의 POL-01~05와 실제 MySQL 데이터 구조/데모 자산 사용권 확인은 구현 시작 전 확인해야 한다. 본 설계는 **기술 계획 기준선 확정**이지 개별 사업 약관이 승인되었다는 뜻이 아니다.
